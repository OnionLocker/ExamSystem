# DSH 出题流程通用性缺口与改进清单

> 目的：把「出题流程本身的缺陷」与「出题人应该只做本职」讲清楚，供改进者在独立上下文里把流程改得更通用、少人工干预。
> 来源：一次真实的 DSH 出题（判断推理 · 真假推理 10 题 + 原因解释 10 题）全程踩坑记录。
> 2026-10-23 二次修订：按 `scripts/quiz_lite.py` 实测核对（临时库回归），修正首版中 B-1 / B-2 / B-5 的错误结论。

---

## 0. 两轨分离：出题本职 vs 流程维护

**出题 agent（DSH 出题会话）只做出题本职，不改任何代码，也不为过闸门手改证据结构或反复换批次。**

### Track A —— 出题本职（出题 agent 只做这个）

1. 抽取参数（模块 / 考点 / 题量 / 难度）；
2. `--plan-only` 取每题考法变式（`kaofa_variant_name`）；
3. 生成题目（一次做对：唯一解、无自相矛盾、情境错开、落在分配变式上）；
4. `--dsh-claims` 取每题待核查原句清单（程序切分，带 `claim_index`）；
5. 派子 agent 审核（盲解官 + 考官 + 独立核查官），组装 review.json；
6. `--dsh-check` 预检（一次报全部问题，不占 batch_id）→ 只修被点名的题 → 预检通过；
7. `--dsh-import` 正式入库；
8. 简报（只报批次名和题量）。

### Track B —— 流程维护（出题 agent **绝不**参与）

- ❌ 编辑 `scripts/**`、`server/**`、`src/**`、`package.json` 等任何代码；
- ❌ 自己写脚本切分解析原句、手工拼 `claim_index`（用 `--dsh-claims`）；
- ❌ 为绕开目录占用反复换 `batch_id`（失败重导直接沿用原 id）；
- ❌ 手跑闸门 / 手写 questions.json / 手签收据；
- ❌ 把"流程缺陷"当成"题目问题"去重写本来正确的题。

> **判断信号**：冒出「改代码 / 自己算原句编号 / 换 id / 手跑闸门」任一念头，说明命中了未自愈的缺口。就地停下：按第 4 节把当前批跑完，把缺口按第 2 节格式记入 backlog。

## 1. 已落地（维护轨不必重做）

| 缺口 | 现状 | 落点 |
|---|---|---|
| 批内 stem 撞题 | 导入时查，`DUP_RATIO=0.82` | `duplicate_question()` |
| 变式 `variant_match` 核验 | DSH 与服务器两路径都要求 `ok=true` 且 `reason` 非空 | `build_dsh_review` / `review` |
| **B-1** 断言证据格式 | `--dsh-claims` 输出与闸门同一切分的原句清单；审查方每条写 `claim_index` **或**直接抄原句 `claim`，脚本对齐成闸门格式。缺句、对不上、缺依据、`valid=false` 逐条报出，**不代填通过** | `dsh_claims()` / `align_claim_checks()` |
| **B-2** batch_id 与变式解耦 | 变式种子 = module + 蓝图的哈希，换 id 不重排 | `main()` |
| **B-2/B-4** 失败重导占用 batch_id | DSH 导入先在 `.dsh-staging/` 签收并过闸门，通过才落正式目录；失败证据移到 `_dsh-failed/` 留档。同一 batch_id 可直接重导，是否已入库由数据库检查把关 | `main()` / `archive_dsh_residue()` |
| **B-5** `usage_checks` 口径 | 首版"DSH 不校验 usage_checks"是**错的**：DSH 签出的收据同样经 `generation_gate.verify`，判断推理（v9）、言语（v7）都按 `claim_index` 逐句校验。现已在导入阶段同口径对齐并预检，不会再签收后才失败 | `build_dsh_review` |
| 全量预检 | `--dsh-check`：临时目录跑完导入校验 + 签收 + `verify`，不写批次目录、不登记、不入库 | `main()` |

> 首版 B-1 曾改为"缺省 necessity_checks 时自动全部判通过"，等于取消了数量题唯一的逐句断言核查，已撤回。

各模块需要的断言字段（`--dsh-claims` 的 `fields` 会直接告诉你）：

| 模块 | 原句范围 | 考官 `necessity_checks` | 独立核查官 `usage_checks` | `question_check` |
|---|---|---|---|---|
| 数量关系 | 含"只能/必须/必然"的句子（常为空） | 覆盖全部 | — | — |
| 言语 | 含用法限制词的句子 | 覆盖全部 | 覆盖全部 | — |
| 判断推理 | 解析**每一句**（按。！？；切） | 覆盖全部 | 覆盖全部 | 必填，reason 以 `PASS` 开头 |

## 2. 改进 backlog（待维护轨落地）

> 每条：问题 → 根因 → 改进动作 → 验收标准。

### B-3 【已落地（演绎题）】生成阶段机械预检：唯一解穷举 / 前提-结论一致性

- **问题**：真假推理出现双解、背景与结论自相矛盾，靠盲解官/考官事后发现，出题 agent 反复重写。
- **落地**：翻译推理、真假推理、组合排列-单题由出题方附 `formal`，`scripts/logic_model.py` 穷举判定；`--dsh-claims` 即报双解/无解/题干矛盾/复述已知条件，判定通过的题免独立核查官，闸门入库前亲自重判（Hermes 同一机制）。
- **剩余**：直言三段论等跨对象量词题仍走 `formal_skip` + 逐句审核；论证类（加强、削弱等）不适用。

### B-6 【中】review.json 组装仍靠出题 agent 手工合并

- **问题**：按 ≤5 题分组派子 agent 后，出题 agent 要手工按全局题号合并盲解 / 考官 / 核查官三份输出。
- **改进动作**：提供 `--dsh-assemble`，读各子 agent 输出文件，按题号合并并做字段完整性检查。
- **验收标准**：出题 agent 不再手写 review.json 结构。

### B-7 【低】plan-only 与 import 之间变式权重漂移

- **问题**：变式分配还受近 30 天账本与近 90 天正确率加权；若两次调用之间有新批次入库或用户作答，同一蓝图可能分到不同变式，而闸门只核 `ok=true`，不比对变式名。
- **改进动作**：review.json 可携带 plan 的 `kaofa_variant` 列表，导入时比对，不一致明确报"变式分配已变化，请重跑 --plan-only"。
- **验收标准**：变式漂移不会静默入库。

## 3. 闸门与审核角色的职责边界

- **机械可验的**（原句切分、断言覆盖、stem 相似度、解析过短、选项排序、收据一致性）由脚本做，`--dsh-claims` / `--dsh-check` 提前暴露；
- **语义判定的**（答案唯一、断言是否成立、是否贴真题、是否落在变式解题动作、难度档位）由子 agent 做。
- 脚本只做格式对齐，不替审查方给出任何"成立"判定。

---

## 4. 命中缺口时的临时工作方式（不动代码把当前批跑完）

1. **预检/导入被拒** → 按报错只修被点名的题或补对应核查（缺哪句补哪句），已通过的题原样保留，沿用同一 batch_id 和 blueprint 重跑 `--dsh-check`。
2. **断言核查** → 先 `--dsh-claims` 拿清单交给考官 / 核查官逐句判；改了解析就重新取清单（原句会变）。
3. **报错看不懂或疑似流程问题** → 把 `message` 原样反馈用户并记入 backlog，**不手跑闸门、不改 questions.json、不改代码**。

---

## 5. 验收北星指标

- 出题 agent 全程 **0 次** 编辑代码、**0 次** 自己切分原句或拼编号、**0 次** 因目录残留换 `batch_id`；
- 单批重试只来自**题目内容质量**，不来自证据格式。
